## FINANCIAL Notes

Observed dominant domains:

- `ealerts.bankofamerica.com`
- `betterment.com`
- `notification.capitalone.com`

Observed dominant signal patterns:

- debit card used
- credit card transaction exceeds alert limit
- automatic deposit is happening soon
- statement is available

What the current taxonomy gets right:

- it can detect at least one `statement_ready` style message

What it is missing:

- card activity alerts
- alert-threshold breach notices
- scheduled deposit / auto-investment notices
- institution-specific statement-ready language beyond the current narrow terms

Likely taxonomy additions or refinements:

- `card_activity_alert`
- `spend_threshold_alert`
- `scheduled_deposit_notice`
- richer statement-ready phrases for Betterment, Bank of America, and Capital One style mail

Noise to watch:

- some `FINANCIAL` labels are clearly promotional or retail-style noise, so sender-domain hints should not be over-trusted without content support

## INVOICE Notes

Observed dominant domains:

- `robinhood.com`
- `uber.com`
- `statefarmservice.com`
- `post.applecard.apple`
- `google.com`
- `service.paypal.com`

Observed dominant signal patterns:

- account statement available
- monthly statement
- card statement ready
- bill ready / auto-payment scheduled

What the current taxonomy gets right:

- some `invoice_ready`
- some `receipt_issued`
- some `generic_invoice_update`

What it is missing:

- broader statement-ready coverage
- bill-ready plus auto-pay scheduled variants
- Apple Card / Google Fi / PayPal statement language
- utility and insurance billing notices that read more like statements than invoices

Likely taxonomy additions or refinements:

- widen `invoice_ready` terms toward `statement_available`, `statement_ready`, and `bill_ready`
- consider a separate `account_statement_ready` subtype if invoice semantics stay too broad
- add sender-domain hints only after the content language is widened

Noise to watch:

- some travel or reservation-related mail is labeled `INVOICE` but does not really belong there
- some policy/privacy notices from finance companies are not invoice mail and should not shape the taxonomy too aggressively

## Cross-Family Takeaways

The sample pass shows a few consistent themes:

1. The YAML skeletons are enough to prove the shared-core architecture, but not enough for real mailbox quality.
2. Sender-domain concentration is strong in every family, which means domain hints will help, but only after phrase coverage is widened.
3. The first useful taxonomy expansion step is not templates. It is Phase 3 signal coverage.
4. `review_needed` is the right fallback for these families right now because the detector maturity is still low outside the best-fit pockets.
5. SHIPMENT is closest to useful real-world coverage after ORDER because Amazon shipment language is already landing.
6. SECURITY has the largest taxonomy gap from live mailbox reality.

## Recommended Next Tuning Order

1. `security`
2. `financial`
3. `invoice`
4. `shipment`

Why:

- `security` is the furthest from live mailbox patterns
- `financial` has dense repeated alert language worth codifying quickly
- `invoice` has meaningful signal already, but its boundaries need sharpening
- `shipment` already has some real hits and mainly needs additional subtypes

## Prompt-Strategy Dependency

These sample artifacts should be reviewed before deciding whether one generic AI template-generation prompt can cover multiple families.

What the samples suggest right now:

- `shipment` and `order` are still the closest pair structurally
- `invoice` and `financial` may share some statement/invoice extraction patterns
- `security` likely needs a distinct schema and possibly a distinct prompt because its extraction targets differ more sharply from the transactional families

That does not yet prove the generic prompt is impossible, but it does suggest the shared prompt contract must be flexible enough to handle very different Phase 4 schemas.
